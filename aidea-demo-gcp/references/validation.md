# 验证与交付

根据已确认的方案主张，选择最小但完整的验证集。默认交付方案总览、按确认领域组织的 Tabs，以及在启用 AI 时独立的首位 AI 智能对话 Tab；同时交付 SOLUTION.md、PLAYBOOK.md、VALIDATION.md、`validation-record.json` 与 manifest。网站相关任务另交站点检查记录。视频交付不属于本 Skill。

## 验收步骤

1. **方案一致性**：确认方案总览呈现已确认方案，Tab 名称/顺序/职责与方案一致，方案主张映射到真实 Demo 操作或清楚标记后续接入。split启用AI时左侧常驻对话、右侧顺序为solution、业务领域；tabs兼容布局顺序为chat、solution、业务领域；不启用 AI 时不强制显示 chat。
2. **版本与数据**：检查 V1–V3 兼容、V4 配置、未知字段拒绝、映射/类型/日期/主键/关系、来源分隔和对账；验证无效输入有明确结果。
3. **分析结果**：以已知样本核对指标精确值、领域筛选、分组、趋势、下钻、空值与零分母；看板、领域问答、API 使用同一范围。
4. **业务状态**：走已确认的重要闭环和必要分支；检查失败不改状态、取消不显示成功、重复点击不重复执行、条件变化使旧建议待重评、跨领域可回读操作结果。
5. **导航与体验**：检查 `#tab=chat` 与 `#tab=solution` 直达、业务 Tab 顺序、前进/后退、切换后上下文不串用、刷新恢复和重置；启用AI时确认split只有一份常驻对话或tabs仅首Tab对话；split补充验证见[分栏工作区](split-workspace.md)，`domainId=solution` 只是只读上下文而非权限或动作入口。检查标题与 Tab 栏固定、内容区独立滚动。默认中文的说明与客户网站体验语言分别验证，覆盖按钮、空状态、错误与确认；按实际交付受众检查桌面和移动端。
6. **AI**：本地 test 模式通过 ADK Runner 与可控模型，证明接口、工具和上下文合同。只有 AI 指令或工具行为发生变化且该路径影响验收时，才做最小必要真实模型场景；真实模型质量需独立记录。一次真实响应不证明整体方案准确。公开摘要与工具过程复用同版本本地测试和UI证据，确认无摘要/无工具调用时不伪造过程；模型或输出合同变化时才增加必要真实场景。

## 证据与状态

每个验收项记录输入、配置/源码摘要、环境、实际结果和证据位置。区分静态/本地模拟、ADK 测试模型、真实模型、真实系统和云端部署；任何一层通过不推导其他层。

只有执行后可回读的结果才标记 `verified`。配置声明不代表通过；模拟步骤记 `simulated`；未执行记 `unverified`；后续接入记 `planned`。源码、方案、配置或数据变动后，引用了旧版本的证据需标待复验，不删除历史记录。

`validation-record.json` 保存结构化验收证据：顶层含 `version`、`status`、`basis`、`entries` 和 `history`；初始为 `pending` 且 `entries` 为空。每条 `entries` 记录 `id`、`status`、`evidence` 与对应的 `basisDigest`。完成实际验证后再填写证据和状态。生成器会初始化该文件，并在后续配置更新时根据运行时源码及 spec/scenario 摘要刷新依据。

可在 Demo 目录外运行 `node /abs/aidea-demo-gcp/scripts/validation.mjs --app /abs/demo` 刷新依据并检测运行时源码或配置是否变化。该命令只计算依据，不执行验收，也不会自动把条目标为通过。源码、`demo-spec.json` 或 `scenario.json` 变化时，它会将顶层状态改为 `needs-revalidation`、把原 entries 标记为过期并存入 history；无变化时保留已有状态和证据。

生成器 `--update` 会更新兼容的 spec/scenario、manifest 和 `validation-record.json`；发现依据变化时同样标记 `needs-revalidation` 并归档旧证据。它不会覆盖人工维护的 `SOLUTION.md`、`PLAYBOOK.md` 或 `VALIDATION.md`。更新后仍须核对这些文档是否与新配置一致，并重做受影响验收。

生成器的 `generationMs` 仅覆盖校验、导入、复制和机械文档生成；依赖安装、构建、测试、AI/网站调研与人工确认分别统计。manifest 记录模板复制代码量，不自动统计客户新增/改动代码；需要报告扩展代码量时另行实际测量并说明口径。实际 Token 或费用无法取得时标记 `unknown`，不推算节省比例。失败请求也不能记为免费。

配置更新不覆盖人工方案或验收记录；更新后回读它们与当前方案/数据是否匹配。交付时提供 Demo 地址、访问方式、方案与验证结果，并明确未执行项及后续条件。

## V4 快速验收

优先运行[快速生成流水线](fast-generation.md)，不在 `npm run build` 后又重复 typecheck。完整流水线测试使用本地 ADK 测试模型，不调用 Gemini；真实模型仅在已有授权且合同变化需要时运行必要场景。

assistant-ui 需验证消息、卡片、follow-up、Enter/换行、停止、错误、刷新恢复、完整消息对历史、重置及桌面/窄屏。业务能力验证原币分区精确值与来源钻取、映射核实依据、关联工作项待重评、普通流程回执与幂等。问答与 UI 使用同一个服务端分析提供者；V4 默认摘要不带整批记录，精确记录按只读工具查询。

`finalize.mjs` 只接受对应应用通过且 basis 未变的流水线报告。手工证据 JSON 使用同一 basisDigest；cases 每项 id/status/evidence，evidence 指向实际文件。只复制显式证据，打包不带 node_modules、dist、私有环境文件或运行日志。打包输出在应用目录外，拒绝覆盖；归档内验证报告和证据使用相对路径。缺手工验收显示 manual-pending，不推导真实模型、容器或云端通过。

完整流程验证须标明已到达的阶段：调研、方向选择、完整方案确认、生成、业务验收、交付。不得用生成器测试代替客户确认，不得将旧客户Demo测试冒充本次新方案端到端通过。已有确认只对范围未变的部分有效。

## 无云与混合模式

对照确认的execution验证，不以test模式代替正式simulated交付。无Google配置样例需保留模拟对话、合成数据看板与动作回读；在缺失项目/无效ADC路径下启动并验证，无真实模型或云调用。检查经营回复与当前筛选/记录/事件一致，范围外问题明确拒绝，工具失败不当成功。模型模式、数据后端及数据来源分别显示。混合模式用本地工具替身验证绑定，不因模式新增重复真实问答；云错误不能自动降级。前置检查权限/网络失败应为unknown，不是absent。
